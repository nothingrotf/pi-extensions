### Autopilot-full

**You own the verdicts, never the PRs. One owner role carries each PR from build to merge, and nothing merges until your verifiers, which never wrote the code, have proven the code that lands.**

A verdict covers one patch and green CI covers one head. Step 4 runs a full swarm once, and again only for a major change. The patch-id rule in `playbooks/shipping.md` can carry a lane's result, and every new head needs its own green CI.

1. **The operator's gates come first.** The grant covers only the queue's items, so items the operator names as theirs and PRs outside the queue stop at merge-ready. A request to state the plan is not a go.
2. **Spawn one owner per PR, and keep its work where a replacement can find it.** Use GitHub CLI (`gh`) for every PR operation. Never require Graphite (`gt`). For each PR, create a linked worktree on its own branch off trunk and dispatch one background `poteto-agent` in place there, per Repository writer in `../references/task-contracts.md`. Use the implementation role of the matched playbook, such as `role: "feature"`, with `capability_profile: "pstack-leaf"`, or `pstack-nested` when the owner must delegate. The owner builds, opens its PR per `playbooks/opening-a-pr.md`, proves the change on the real artifact, and reports the code-ready head.

   Open the PR early so CI and bots run alongside the work. The code is ready only after the `/deslop` and `/no-comments` passes, so the full swarm runs on finished code. Then rebase onto current trunk and report the code-ready head before self-proof, so verification runs on the base the patch lands on. Run the repository's checks for the touched paths on the committed head before the code-ready push. Run the slow suites that CI already runs only in CI, unless the brief names a local reason. Fix rounds stay on that base unless trunk conflicts, breaks CI, or lands a known concurrent change to the same files, because each rebase restarts CI.

   Push each finished unit before you start the next. Each owner Task ends when it reports. A fresh owner with consolidated scope takes each later round in the same worktree: fixes, merge prep, and the merge. Keep a decision trail per the **show-me-your-work** skill under `~/.pi/agent/poteto/`, and record each agent's id, state, and a stuck-after runtime from past runs of its kind. Force-push only the owner's own branch. Before a rewritten push, verify the remote tip with `git ls-remote` and push with `--force-with-lease=<branch>:<observed-tip>`. On any push the run did not make, stop and report to the root. Never force-push a shared branch.
3. **Run owners in parallel off trunk, never stacked,** so each PR lands on its own. Run in parallel only owners whose files, dependencies, and mutable resources are disjoint. Route dependent work to Autopilot-stack.
4. **Swarm-verify once.** A full swarm runs once, at the code-ready head. Another full swarm runs only for new behavior, a redesign, or a large new diff. A rebase, a merge-conflict resolution, or a minor fix gets a single verifier at the new head, and a wording-only change gets none. Fan out independent verifiers at the code-ready SHA per the **swarm** skill. They re-run the gates, prove the load-bearing behavior live on the real surface through its control skill (`control-ui` or `control-cli`) or a named driver, and audit the diff. The verdict is not clean without the live lane, or before you audit the merge-ready report's receipts, because no lane trusts a claim it has not checked.

   Block a PR only for a problem you can show, with a failing run at the head or a doc line the PR made wrong. A problem the PR's base already has, whether trunk or the PR below it in a stack, doesn't block unless the PR copies it or newly reaches it. Only a bug a user would hit, a failed gate, or a wrong shipped doc blocks, and everything else goes in a follow-up. Send every blocking finding to a fresh owner in one fix-forward, with a red test across every site with the same defect. Never push a fix yourself, because each branch has one writer. Replace a stuck owner instead.
5. **The owner merges only what you verified, tested on the trunk it lands on.** Green CI alone never authorizes a merge. Once the swarm's lanes have started, merge prep rebases onto current trunk, reports the new head, and waits for green CI.

   Right before merging, fetch trunk and ask whether its changes can affect the patch, because rebasing for every trunk move never ends. Rebase and wait for CI when the code that would land was never tested, as with a conflict, a file both sides changed, or a change to which checks run for the PR. A lockfile both sides changed needs no rebase when a frozen install passes on the merge result and the packages the PR changes resolve there as on the head, because that install tests the lockfile that would land, and a failing install means the rebase must repair it. When trunk changed a caller of the patch or something the patch depends on, such as code it calls or a dependency version, run the patch's checks on the merge result and merge on a pass. Otherwise merge with `gh pr merge <pr> --squash`. If trunk would force a third rebase past merge prep, hold and report to the root, which sequences the colliding work. Remove the PR's worktree after it merges.
6. **Run the root layer.** Babysit each open PR from the root per `playbooks/babysit.md`, because the root owns the installed loop and the watcher. Use `background` while builds continue. Anything that loosens a gate, such as a raised budget or an allowlist entry, needs a verifier's proof and then your fresh countersign, because the owner is the one who wants green. A disabled or soft-failed check always comes out, because it stops guarding every case. Never give or bypass an approval the forge enforces, because no countersign covers it.

   On the operator's go, arm `/loop 1h` through the installed `loop` skill to audit until no delegated work is left, because long runs drift and agents stall silently. Use `TaskControl` with `action: "wait"` when no independent work remains. Never use shell `sleep` to await children. Each tick fixes drift, such as an unreported head or an unrecorded agent, by having its owner record it. It probes every agent, down to the leaf lanes, and judges each by its side effects, such as commits, pushes, and PR changes, because status text can hide a stuck child. An agent is stuck when it errors, cannot start turns, or shows nothing new past its stuck-after runtime. One waiting on you or the operator is not stuck, so answer it. Cancel a stuck writer, then replace it from its retained scope. A tick that changed something for the operator ends by catching them up per the **ketchup** skill, and one that changed nothing stays quiet.
7. **Stand down at once on the operator's stop.** Cancel running writers for a zero-writes order. Steering alone does not stop an in-flight write. Keep each owner's brief and trail until the operator releases the hold.

**Reply:** catch the operator up per the **ketchup** skill, covering each PR's state and verdict, what merged, countersigns and why, open operator gates, and parked follow-ups, with links to each PR and the trails.
